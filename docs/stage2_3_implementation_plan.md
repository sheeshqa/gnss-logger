# Stage 2.3 — план UTC-ротации UBX

Дата: 2026-10-28. Основа: 0.4.0.dev2, cd12c1c3f2f899cce7942023c220146ec727495d.
**Это проект решения для согласования. Код, схемы и CLI этим документом не изменены.**
Аппаратная основа: локальный аудит Stage 2.2 (личный отчёт не публикуется), PASS WITH LIMITATIONS
по трём diagnostic JSON; фактические UBX/manifest/checkpoints/events этих запусков не переданы.

## 1. Цель и границы

Добавить к record производные файлы по UTC-суткам с понятными именами, сохранив точный
первичный журнал принятого потока. Каждое допустимое UBX-сообщение целиком попадает ровно
в одну датированную либо undated-проекцию; первичный журнал сохраняет также повреждённые,
неопознанные и незавершённые байты. Проекции не заменяют оригинал.

Включено: именование и резервирование, framing, политика времени, ротация, хеши,
метаданные происхождения, корректное закрытие и тесты отказов нового writer.

Не включено: автоматический reconnect (2.4), полноценное recovery (2.6), автоматическое
удаление, RINEX/TEC/ROTI, Drive, GUI. Усиленная защита диска, мониторинг/сон и длительные
испытания остаются соответствующими пунктами утверждённого roadmap 2.5/2.7/2.8.
Обработка ошибок новой проекции нужна уже здесь; она не означает реализацию всего 2.5.
Не переносить старые файлы, не дописывать существующие завершённые UBX.

## 2. Что сохраняется и что необходимо добавить

Сейчас один Reader владеет COM, bounded queue передаёт chunks контроллеру, JournalSink
пишет исходные байты, Diagnostics анализирует поток. Сохраняются queue defaults 8 МиБ,
sync 1 с, учёт accepted write prefix, SHA/read-back, read-only guard, идентификация
MON-VER и отдельные адаптеры F9P/X20P. Новых команд приёмнику для ротации не требуется.

Ограничения существующих компонентов:

- UTCWriter с датой чанка не годится для точной границы UBX-сообщений.
- rawx_utc выполняет преобразование, но не заменяет политику доверия и скачков времени.
- UBXParser ограничивает payload диагностическим порогом 16384 байта; для полной
  UBX-проекции нужен разбор до протокольного предела 65535 байт, включая неизвестные class/id.
- Общий storage_failed нельзя распространить на daily writer: отказ копии не должен
  отключить сохранение очереди в исправный первичный журнал.
- Схемы v1 не описывают ROTATION, диапазоны происхождения и durable frontier проекции.

Это требования интеграции следующего этапа, не доказанные потери Stage 2.2.

## 3. Поток данных и владельцы

```text
COM -> единственный Reader -> ограниченная очередь -> primary journal
                                                  + receipt index
                                                           |
                                              synced/committed prefix
                                                           v
                                      ProjectionCursor (читает файл, не COM)
                                                           |
                                         lossless framer + TimeResolver
                                                           |
                                       DailyProjector -> *.ubx.part
                                                           |
                                         bounded verification worker
                                                           |
                                         no-replace publish -> *.ubx

Controller -> events, checkpoints, artifact records, manifest, report
```

Primary всегда записывается первым. Проекция читает только подтверждённый synced prefix
журнала, небольшими блоками; последняя часть проецируется после финального sync.
Это допускает задержку daily примерно на sync interval и не обещает секундный срок при
перегрузке диска. Задержка/cursor backlog видимы в диагностике. В RAM не копится дневной поток.
Framer держит ограниченный буфер сообщения (до 65535+8 байт) и ограниченный read buffer.
Неразрешённые диапазоны времени хранятся как offsets на диске, не как растущий список bytes.

Добавить append-only receipt index: source offset/length, chunk sequence, host received UTC
и monotonic timestamp. Он связывает время получения с journal offset, не меняя журнал.
Это нужно, чтобы TTL времени зависел от получения, а не от задержки чтения проекцией.
Для кадра используется время получения его последнего байта. Sync/checkpoint фиксирует
общий подтверждённый префикс journal и индекса; хвост без индекса после аварии не получает
вымышленного времени. Индекс не является вторым владельцем COM.

Закрытый большой файл проверяется одним worker с ограниченной очередью задач, чтобы
read-back SHA не блокировал получение данных на полуночи. Worker возвращает результат
единственному владельцу метаданных; не пишет manifest сам. До проверки файл остаётся .part.
При остановке закрыть read handles проекции перед переименованием primary на Windows.

## 4. CLI и каталоги

Предложение: сохранить поведение record без новых опций и добавить опциональный
`--daily-root`. Существующий --output продолжает обозначать корень служебных runs.
Пример **будущего, пока не реализованного** интерфейса:

```powershell
gnss-logger record <существующие параметры подключения> `
  --output "$env:LOCALAPPDATA\GNSS\internal\runs" `
  --daily-root "$env:LOCALAPPDATA\GNSS\data"
```

Точное написание всех старых параметров сохраняется; этот пример не является командой
для аппаратного запуска. Идентификатор станции берётся из существующего --station/settings.station;
проверить безопасный компонент пути: запрет traversal, разделителей и Windows reserved names.
Нет daily-root — прежняя запись 2.2 и прежние схемы v1. serial/replay/mock/ports не меняются.

```text
GNSS/
  data/
    UBX1/
      2026/10/
        UBX1_20261028.ubx
        UBX1_20261028_001.ubx
        UBX1_20261029.ubx.part          # пока открыт или проверяется
      undated/
        UBX1_undated_001.ubx
  internal/runs/
    <run_id>/attempts/<attempt_id>/
      manifest.json
      report.json
      events.jsonl
      checkpoints/
      artifacts/<artifact_id>.json
      <первичный журнал в существующем формате имён>
      <receipt index и projection range index>
```

Никакой автоматической миграции. Корни локальные, вне репозитория и OneDrive. UUID остаются
в служебных записях, не добавляются в пользовательское имя. Все final/temp пути связаны
с artifact_id, run_id, attempt_id и connection_id; связь не восстанавливается догадкой по дате.

Будущие OBS/NAV смогут наследовать basename и artifact provenance. Их создание не входит
в 2.3; исходный UBX и служебные данные сохраняются независимо от конвертации.

## 5. Имена и защита от коллизий

Первое имя: STATION_YYYYMMDD.ubx; следующие: _001, _002, ... . Разрядность минимум три,
после _999 допустимо _1000. Дата всегда из GNSS-derived UTC. Для undated — отдельная
последовательность STATION_undated_001.ubx. Нумерация может иметь пропуски.

Проверки exists недостаточно. Для каждого кандидата атомарно создавать соответствующий
*.ubx.part в exclusive mode xb. Это одновременно резервирование имени и рабочий файл.
Final, part и ранее занятое/аварийное имя считаются занятыми. После захвата part повторно
проверять final: если он уже есть, отказаться от кандидата и взять следующий суффикс.
Разрешается удалить только собственный только что созданный пустой reservation до первой
записи; никакие старые файлы/чужие parts не трогать. Оба процесса используют один протокол
на общем daily-root, даже если internal roots различаются.

Публикация только no-replace. Если чужой final появился после резервирования, оставить
свой part с данными, зафиксировать конфликт и остановить проекцию; не заменять final.
Старый part после force kill не переиспользовать и не считать безопасным только по PID.
Новый запуск выбирает следующий суффикс. Не append в закрытый/старый файл, не объединять
сеансы. Возврат на уже использованную UTC-дату после разрыва также создаёт новый сегмент.

До первых байтов проекции сохранить durable intent: artifact_id, source journal ID,
путь part/final, владельцы и причина открытия. Сбой между reservation и intent оставляет
пустой зарезервированный part, а не разрешение перезаписать его при следующем запуске.

## 6. UTC-привязка

### Источник и предел доказательств

RAWX содержит GPS week, receiver-local rcvTow и GPS–UTC leapS; валидность leapS и clockReset
задаются recStat. Базовое преобразование при валидных полях:

```text
UTC = 1980-01-06T00:00:00 + week * 604800 s + rcvTow - leapS
```

Поля описаны в официальном [F9 HPG 1.51 Interface Description, RAWX §3.17.6](https://content.u-blox.com/sites/default/files/documents/u-blox-F9-HPG-1.51_InterfaceDescription_UBXDOC-963802114-13124.pdf)
и [X20 HPG 2.02 interface JSON](https://raw.githubusercontent.com/u-blox/u-blox-X20-interface-description-json/main/HPG/u-blox-X20-HPG-2.02.json).
F9 документ относится к более новой firmware/protocol, чем испытанные HPG 1.13/27.12:
он не доказывает полную совместимость всех ключей старой firmware. Для крайних временных
ситуаций сверить архивную документацию именно HPG 1.13 перед реализацией. X20 аппаратно
не проверен; его адаптер не наследует неподтверждённые конфигурационные ключи F9P.

Не использовать постоянное 18 вместо leapS, локальную дату Windows, UTC хоста, время
записи файла или GNSS-время из другого масштаба как дату наблюдений. Часы хоста применяются
к диагностике/TTL и не корректируют исходные измерения. Приёмник не перенастраивается.

### Предлагаемые состояния TimeResolver

| Состояние | Условие и действие |
|---|---|
| UNDATED | Нет приемлемого якоря; полные кадры идут в undated |
| CANDIDATE | Первый приемлемый RAWX; ожидается подтверждение последовательностью |
| VALID | Два последовательных согласованных RAWX; доступна дата и generation |
| DISCONTINUITY | Reset, скачок, неприемлемые поля или противоречие; сброс доверия, новый generation |

Проверять checksum/версию/длину RAWX, finite rcvTow, допустимый диапазон week/TOW,
leapSec validity, clockReset, последовательность эпох. Нулевые/неправдоподобные недели
не объявлять текущей датой. Предлагаются два подтверждающих якоря и TTL=max(5 с, 3P),
где P — ожидаемый интервал наблюдений, не команда настройки приёмника. Точные пороги и
допуски должны быть согласованы и вынесены в документированную политику.

Сравнивать GNSS delta с monotonic arrival delta: реальный пропуск эпох не равен сбросу
часов, а необъяснимое движение назад/вперёд требует новой generation. Фиксировать оба
вида событий; не заполнять пропуски, не изменять rcvTow/фазу/порядок сообщений.

### Присвоение сообщений и граница суток

1. Сохранять вход в primary, затем обрабатывать durable frames в порядке source offsets.
2. RAWX с доверенным временем получает собственную UTC-дату. Первый RAWX следующего
   дня целиком открывает новый датированный сегмент; начало синхропоследовательности
   определяет границу кадра независимо от границы read/chunk/sync.
3. SFRBX/MON-VER/прочие кадры без UTC наследуют последний доверенный RAWX-якорь
   в порядке потока, пока TTL не истёк. Кадры до нового RAWX остаются у предыдущего
   якоря. Это правило маршрутизации, не время передачи навигационных данных SFRBX.
4. До первого кандидата обратную привязку не делать. Когда кандидат подтверждён,
   разрешается датировать его собственный RAWX и следующие кадры по подтверждённому
   якорю; предыдущие кадры остаются undated. Неподтверждённый кандидат при остановке — undated.
5. Неисправное/просроченное время, clockReset и неоднозначная смена leapS прекращают
   наследование. Закрыть сегмент с причиной time_discontinuity/time_expired, следующие
   кадры отправить в undated. Новое доверие создаёт новый сегмент/суффикс, даже для той же даты.
6. На потенциальной неоднозначной границе (полночь/смена leapS) держать ограниченный
   look-ahead до следующего RAWX: хранить offsets, а не байты в RAM. При остановке или
   истечении TTL неразрешённые кадры остаются undated. Не перемещать задним числом уже
   опубликованные кадры между файлами.

Python datetime не представляет 23:59:60. Формула сама по себе не даёт полного алгоритма
для вставленной/удалённой секунды. Предлагается консервативная политика: проверить соседние
GPST-якоря и leapS, а спорный интервал сохранить в primary+undated с причиной ambiguity.
Не обещать точное помещение каждого кадра leap second в суточный файл без соответствующей
модели и тестов. NAV-TIMEUTC/TIMELS polling не добавлять молча; вопрос о дополнительных
read-only источниках времени оставить отдельному согласованию.

Фазовые WARNINGS не меняют дату или маршрут кадра. Достоверность UTC означает выполнение
выбранной политики приёмника, а не независимую сертификацию абсолютного времени.

## 7. Сохранение байтов и границы учёта

Lossless framing выдаёт кадры и opaque ranges с абсолютными offsets. Полный кадр с
правильной checksum проецируется в исходных байтах, включая неизвестные class/id;
payload не перекодируется. Ошибочные checksum, noise и незавершённый tail остаются
в primary и явно учитываются; не превращать их в будто бы корректное UBX-сообщение.
MON-VER не копируется дополнительно в каждый день: это создало бы новые сообщения.

Инварианты при нормальном завершении:

```text
received = primary_written + pending + unarchived
primary_synced <= primary_written <= received
primary_bytes == последовательность всех байтов, возвращённых источником
projection_cursor <= committed_primary_and_receipts_frontier
каждый пригодный полный кадр <= projection_cursor -> ровно один dated/undated artifact
```

Для успешного полного завершения pending=unarchived=0, synced=written=received,
проекция доходит до конца, tail имеет явную классификацию. При ошибке остатки не скрываются.
Сумма daily bytes может быть меньше primary bytes на noise/неполные кадры; разность
объясняется диапазонами. Пригодные датированные и undated кадры покрываются без пересечений
и пробелов. Порядок проверяется по source offsets, не лексикографией имён при скачках даты.
Копии daily не прибавляются к received/written/synced первичного Ledger.

## 8. Метаданные и версионирование

Предложение: новые версии v2 manifest/checkpoint/event/diagnostic только для daily-enabled
запусков, с явной версией контракта. v1 остаётся неизменным и читаемым. Нельзя просто сменить
глобальную CONTRACT_VERSION так, чтобы валидатор отвергал старые артефакты; нужен dispatch
по типу/версии и regression fixtures. Старые схемы/JSON/UBX не мигрируют.

| Запись | Дополнения v2 |
|---|---|
| Manifest | primary и derived artifacts, пути part/final, IDs владельцев, first/last RAWX UTC, time generation/quality, storage state, покрытие/partial_day, причина закрытия, bytes/SHA, ссылки на range index |
| Checkpoint | durable primary offset/hash и receipt frontier, projection cursor, time/candidate state, активные reservation/segment IDs, written/synced offsets и хеши derived, подтверждённый range index prefix |
| Event | SEGMENT_OPENED, ROTATION, TIME_BINDING, SEGMENT_CLOSED, PROJECTION_ERROR; old/new day, generation, source offsets, IDs и причина |
| Diagnostic | независимые primary accounting, projection bytes/pending/backlog/errors, time state, версии/runtime/commit когда известен; hardware status без автоматического PASS |

Source ranges хранить в append-only projection index, объединяя смежные ranges. Не
накапливать все кадры в RAM и не переписывать полную историю диапазонов каждую секунду.
Checkpoint содержит cursor/hash подтверждённого префикса индекса. Индексы и snapshots
не предполагают атомарную транзакцию сразу между всеми файлами.

Для каждого закрытого файла — неизменяемая artifact record в служебном каталоге,
чтобы будущая обработка могла увидеть готовый день до конца многосуточного run.
Final manifest остаётся последним commit запуска; report до него сам по себе не доказывает
завершение. CLOSED_COMPLETE по сохранению файла не означает полное покрытие 24 часов:
coverage/partial_day и завершение run — отдельные признаки.

Порядок фиксации: primary+receipts sync -> projection/range index sync -> checkpoint;
при закрытии derived — flush/fsync/close -> read-back SHA -> no-replace publish ->
immutable artifact record и event -> финальный manifest после всех итогов. Ошибка на любом
шаге оставляет описанный незавершённый статус, не фиктивный VERIFIED/complete.

## 9. Ошибки и совместимость с будущим recovery

Разделить primary_failed, projection_failed и metadata_failed. Отказ daily write/sync/hash,
индекса или metadata ставит управляемую остановку; уже возвращённые данные всё равно
дописываются в исправный primary. При ошибке самого primary точно учитывать accepted
prefix и unarchived. Short write не считать полной записью. Отчёт должен сохранять обе
ошибки, если после ошибки проекции откажет и primary.

Bounded очередь verification при переполнении не отбрасывает задачу: управляемый отказ
проекции/останов с сохранением primary. Запретить безграничное число открытых daily файлов
и рост RAM при скачках времени или задержке диска. Проверять обслуживание очереди ingress
даже при backlog проекции; длительный sync/fsync всё ещё может вызвать существующий overflow,
который должен быть явно диагностирован, а не замаскирован.

После force kill допустимы part и последний durable checkpoint, а не обещание сохранения
RAM/кэшей ОС. Новый запуск не append и не «восстанавливает» старый файл автоматически:
новые IDs, новые суффиксы; старые bytes/intent/index/checkpoints нетронуты. Будущий 2.6
сможет сверить durable prefixes, hashes и завершить/пересоздать проекцию отдельно.
Будущий 2.4 создаст connection boundaries/gap events, не склеивая незаметно разрывы;
в 2.3 USB exception по-прежнему останавливает run.

Адаптеры F9P/X20P и read-only policy сохраняются. Не вводить модельно-зависимые ключи
для ротации, не активировать RAWX/SFRBX, не менять rate, RTS/DTR или USB configuration.

| Шаг внутри 2.3 | Результат | Критерий |

## 12. Автономные тесты, которые предстоит добавить

Все времени/источники инъецируемые, без ожидания реальной полуночи. Использовать временные
каталоги и синтетические/разрешённые immutable fixtures; аппаратные оригиналы не изменять.

| Сценарий | Проверяемое свойство |
|---|---|
| UTC полночь внутри read и UBX поперёк chunks | кадр целиком в одном файле, RAWX нового дня в новом файле |
| GPS полночь != UTC полночь, week rollover, месяц/год, 29 февраля | GNSS-to-UTC и каталоги без host-local даты |
| Полная/потенциальная leap second, смена leapS, reset/backward/jump | нет молчаливой ложной даты; ambiguity/новая generation/undated |
| Нет времени -> кандидат -> valid, stale TTL -> valid | нет backfill до кандидата, documented SFRBX inheritance, новый сегмент |
| Много запусков в день, Ctrl+C -> новый run, USB error -> новый run | base/_001/_002; старые файлы не меняются; источник сеанса явно указан |
| Два процесса одновременно, старые parts, внешняя final-коллизия | exclusive reservation/no-replace, отсутствие overwrite/append |
| Останов до/после границы и на каждом publication шаге | очередь дренирована, состояния/commit не преувеличены |
| Force kill отдельного тестового child процесса на barrier | сохранность durable prefix/старых parts, новый suffix; recovery не притворяется выполненным |
| Шум, checksum error, sync pattern в payload, частичный tail | primary byte-identical, opaque учтены, только целые корректные кадры в projection |
| Unknown class/id и payload >16384 до 65535 байт | валидный полный UBX сохранён без перекодирования и необоснованного discard |
| SHA каждого closed файла, range coverage и порядок | no lost/duplicate eligible frames; exact source slices; manifest = фактические файлы |
| Short write, flush/fsync/read-back/publish/index/metadata errors | primary drain при отказе проекции, точный accepted prefix при отказе primary |
| Медленная проверка большого дня, очередь verifier заполнена | bounded RAM/jobs, ingress не блокируется read-back задачей, явный overload |
| v1 fixtures, serial/replay/mock, оба адаптера | обратная совместимость схем/CLI и read-only guard |

Для force kill тест управляет только своим child PID, синхронизируется ready barrier
и проверяет файлы после завершения процесса. Это не аппаратная имитация потери питания.
Проверка целостности должна сравнивать исходные bytes и диапазоны независимым проверяющим
проходом; одних совпавших счётчиков нового writer недостаточно.

Исходная регрессия для сравнения: **147 тестов PASS** 2026-10-28, Python 3.12.14/Windows 11.
Новые тесты ещё не написаны/не выполнены. Проверку Python 3.9–3.15 описывать по реально
доступным runtime; локальный PASS не означает запуск нового кода на рабочем Python 3.15.1.

## 13. Будущие аппаратные проверки пользователем

После автономной приёмки подготовить отдельные точные команды для Windows 10 и текущего
COM/идентификации. Сейчас аппаратные команды не выполняются и реализация не существует.

- 30–60 минут record с daily-root: первичный журнал, readable UBX, actual SHA, полный
  terminal manifest, Replay, range accounting и фаза отдельно от registration.
- Реальная граница UTC-суток: окно по обе стороны полуночи без перевода часов хоста или
  приёмника. Проверить даты крайних RAWX, целые SFRBX, coverage, минимум два daily artifacts,
  событие ROTATION, no loss/duplication по source ranges и независимым bytes/SHA.
- Ctrl+C/USB до и после границы, затем ручной новый запуск: parts/status/суффиксы, сохранность
  исходных файлов, явные границы сеансов. Автоматического reconnect пока не ждать.
- При безопасных условиях отдельный операторский force kill; проверить сохранённые parts
  и checkpoint без объявления полного recovery или гарантии сохранности несинхронизированной RAM.

Все эти проверки имеют статус **NOT TESTED**. X20P — отдельная будущая аппаратная проверка.
Непрерывность нескольких суток и нагрузку 3–7 суток не объявлять проверенными коротким тестом.

## 14. Критерии готовности Stage 2.3

1. Все старые тесты и новые автономные сценарии проходят; старый CLI/v1 не сломаны.
2. Primary содержит точную последовательность returned bytes либо отчёт явно указывает
   accepted prefix/unarchived/error; ошибка проекции не скрывает/не отменяет primary drain.
3. UTC-day policy проверена виртуальным временем; каждый eligible frame целиком и ровно
   один раз в dated/undated output, opaque/tail остаются в primary с диапазонами.
4. Имена понятны, коллизии/parts/повторные запуски безопасны; чужие/старые файлы не меняются.
5. SHA/read-back, source ranges, artifact records, checkpoint frontier и terminal manifest
   согласованы с реальными файлами. Незавершённые артефакты не выдаются за committed complete.
6. Очереди/буферы/verification bounded; диагностируются backlog, сбои и неоднозначное время.
7. Подготовлен отчёт автономной приёмки и инструкция аппаратной. Аппаратный PASS присваивается
   отдельно после получения исходных файлов/свидетельств от оператора; до этого NOT TESTED.

## 15. Риски и решения, требующие согласования

| Вопрос | Предложение и следствие |
|---|---|
| Opt-in и расположение | daily-root отдельно от --output; без опции сохранить 2.2. Старые файлы не мигрировать |
| Неизвестное время | отдельные undated UBX для полных кадров, все bytes также в primary; утвердить вместо primary-only для таких кадров |
| Пороги доверия | два RAWX-якоря, TTL=max(5 с, 3P); уточнить P/допуски, clock jumps и leap ambiguity до реализации |
| Leap second | консервативный undated спорного интервала; нужна ли более строгая модель/дополнительные read-only сообщения отдельным решением? |
| Метаданные | additive v2, receipt/range indexes и ограниченный verification worker: дополнительный I/O и объём, зато восстановимое происхождение |
| Имена | atomic part reservation, пропуски в суффиксах допустимы; никаких автоматических append/очистки старых parts |
| Диск/нагрузка | primary+projection примерно удваивают payload-хранение плюс индексы; измерить backlog и свободное место, не удалять автоматически |
| Stage 2.2 evidence | для безусловного файлового PASS получить три UBX и служебные файлы; текущий статус остаётся PASS WITH LIMITATIONS |

Конфликты требований не скрываются: все исходные байты сохраняет primary, а пользовательские
суточные UBX содержат только целые корректные сообщения; спорное время остаётся undated.
Если требуется побайтовая копия всего шума именно в daily, это другая политика с отдельными
критериями и её следует утвердить до кодирования. В текущем предложении raw originals не теряются.

изменение схем/CLI, commit и push в рамках подготовки не выполнялись.**
