# Stage 3.2 — пакетная конвертация и запись

Stage 3.1 на рабочем Windows 10 с demo5 b34k обработал восемь сегментов со статусом
SUCCESS_WITH_WARNINGS. Для четырёх основных файлов оператор подтвердил совпадение
SHA-256 секций данных OBS и NAV с ручной конвертацией. Расчёты TEC дали 77 и 61
пролёт. Сопоставление входов, параметров блокнота и метаданных заголовков остаётся
отдельной проверкой. Два события invalid_rawx_time относятся к регистрации.

## Windows 10 и 11

Установите обновление в рабочую venv. Укажите фактический путь к convbin.exe
в локальном TOML, подготовленном по [инструкции Stage 3.1](stage3_1_contracts.md).
Для воспроизведения сравнения используйте ту же сборку demo5 b34k.

~~~powershell
$Py = (Resolve-Path '.\.venv\Scripts\python.exe').Path
& $Py -m pip install -e .
$Base = Join-Path $env:LOCALAPPDATA 'GNSS'
$Cfg = Join-Path $Base 'conversion.local.toml'
$InputDir = Read-Host 'Каталог завершённых UBX'
& $Py -m gnss_logger convert --config $Cfg --input $InputDir --dry-run
& $Py -m gnss_logger convert --config $Cfg --input $InputDir
& $Py -m gnss_logger convert --config $Cfg --input $InputDir
~~~

Для выбора по записи используйте convert --run-id с UUID из manifest. Для
повторной конвертации с другим профилем или сборкой задайте новый --output.
Каждый вход обрабатывается отдельно. Для архивного каталога оператор выбирает
закрытые файлы .ubx. Пути .ubx.part исключаются, а пустые, повреждённые и
непригодные для выбранного режима входы получают ошибки по сегментам.

## Фиксация результата

OBS/NAV проверяются и публикуются без перезаписи. Последним публикуется
<basename>.conversion.json с параметрами, SHA-256 входа, исполняемого файла и
результатов, путями и проверкой содержимого. Сводный conversion-<operation>.json
схемы 2 хранит статусы по каждому сегменту и summary.

| Статус сегмента | Условие |
|---|---|
| SUCCESS / SUCCESS_WITH_WARNINGS | Проверенные выходы и зафиксированный результат |
| ALREADY_CONVERTED | Вход, executable, параметры и SHA-256 имеющихся выходов совпали |
| CONFLICT | Имеющийся результат нельзя подтвердить для текущих входа и параметров |
| FAILED | Ошибка входа, процесса, проверки OBS или публикации |
| INCOMPLETE_NAVIGATION | Проверка NAV не пройдена |
| INTERRUPTED / NOT_RUN | Текущий сегмент прерван или до него не дошла очередь |
| DRY_RUN | Проверены исходные данные для плана и показаны команды без публикации |

Для имеющихся результатов Stage 3.1 подтверждением также служит сохранённый
сводный JSON схемы 1. При отсутствии совпадающего подтверждения оставшаяся
после аварии пара получает CONFLICT. Для нового прогона используйте отдельный
выходной каталог. Результаты неудачных сегментов не мешают обработке остальных.
При ошибке запуска всего пакета причина записывается в errors, сегменты отмечаются
NOT_RUN. Если диск недоступен для отчёта, ошибка выводится в JSON через stdout.

## Закрытые сегменты во время записи

К своей рабочей команде record с --daily-root добавьте --convert-config $Cfg.
Например, для уже подготовленных аргументов записи из аппаратной инструкции:

~~~powershell
& $Py -m gnss_logger record @Common --seconds 1800 --convert-config $Cfg
~~~

Сегмент передаётся отдельному потоку после проверки SHA, публикации .ubx и
записи CLOSED_COMPLETE. В очередь попадают и закрытые undated-сегменты. Для OBS
сегменту нужны пригодные RAWX. Один поток вызывает convbin последовательно, пока
регистрация продолжается. После остановки регистрации CLI ждёт обработки принятой
очереди. Очередь в памяти рассчитана на 32 ожидающих сегмента. При переполнении
счётчик deferred увеличивается, а артефакт остаётся доступен для пакетного запуска
по успешному terminal manifest. После аварийного завершения процесса также можно
запустить конвертацию закрытых .ubx по явному архивному пути.

Статус записи описывает целостность регистрации. Статусы конвертации и deferred
сохраняются отдельно в conversion-summary.json каталога попытки и stdout команды.
Каждая конвертация имеет свой JSON-отчёт в выходном каталоге RINEX.

## Приёмка

Для сквозной приёмки на рабочем ноутбуке выполните короткую запись с опцией
конвертации, затем прогон тех же восьми архивных UBX в новый каталог и повтор
в тот же каталог. Сравните секции данных OBS/NAV после END OF HEADER с результатами
Stage 3.1 для каждого сегмента. Для подтверждённых пар повтор должен вернуть
ALREADY_CONVERTED. Сохраните отчёты, SHA-256 и список исходных сегментов.

### Автономные испытания от 2026-11-13

На Windows выполнено `python -B -m unittest discover -s tests -v`.
Все 200 тестов прошли без пропусков. Пакет из восьми синтетических UBX проверил
первую публикацию, повтор и обнаружение изменённого NAV. Проверены совместимость
со сводным JSON Stage 3.1, прерывание, повреждённые входы, имитация ENOSPC и
коллизия имён. На синтетической записи через CLI проверена фоновая публикация
и повторное использование результатов, а также отсутствие convbin.

Сквозная приёмка Stage 3.2 на восьми исходных сегментах с demo5 b34k ожидается
на рабочем ноутбуке. В домашнем окружении сценарии вызова RTKLIB проверены
подменой subprocess.
