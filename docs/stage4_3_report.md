## Управление и безопасность

- При запуске окна нет автоматического открытия/перечисления портов: пользователь нажимает «Обновить».
- Модель подтверждается MON-VER; USB VID/PID/serial/location сверяются с выбранным устройством.
- Start требует подтверждённой привязки. Смена порта, baud, неверный baud или Refresh сбрасывают её.
- Идентификация/диагностика работают в фоновом потоке; команды конфигурации не добавлены.
- Запись использует существующий контроль владения устройством; повторный Start и диагностика во время записи запрещены UI/coordinator.
- Stop вызывает существующий API остановки. Владение сохраняется до результата и завершения worker, а не только до получения terminal event.
- Закрытие окна с активной операцией требует подтверждения и асинхронно ждёт сохранения данных.
- При сбое мониторинга запрашивается Stop, но UI не освобождает операцию до фактического завершения.
- Отображаются исходные счётчики API, ошибки, registration, integrity, phase_quality, артефакты и пути; GUI не пересчитывает научное качество.
- События доставляются в UI-поток ограниченными подтверждаемыми пакетами; длительное ожидание результата выполняется worker.
- Поздний Stop не переводит уже завершённую операцию обратно в STOPPING; ошибки создания монитора освобождают незапущенный handle.

## Проверки

Окружение: Windows 10 x64, Python 3.15.1, PySide6-Essentials/shiboken6 6.12.0,
pyserial 3.5. Qt-тесты выполняются с offscreen platform, а не на реальном мониторе.

Первый связанный прогон: 44 теста, 43 PASS и 1 FAIL. Пятисекундный тест успевал
завершиться до первого чтения synthetic source из-за времени инициализации хранения.
Тест изменён: неограниченная запись, ожидание двух RAWX-эпох с защитным deadline,
Stop и проверка manifest/байтов/SHA-256. Production recorder не изменялся.
Повтор: **44/44 PASS**, 25.942 s.

Smoke: `python -m gnss_logger.gui --mock --smoke-test` — **PASS**, exit 0.
Идентификация, Start, получение RAWX, Stop, STOPPED_COMPLETE, exit_code=0,
unarchived=0, закрытие и доставка в UI-поток подтверждены. Heartbeat: 98.
Это синтетическая запись, не аппаратная сертификация.

Первый полный прогон: **349 total, 346 PASS, 2 FAIL, 1 SKIP**, 82.643 s.
Два FAIL совпадают с [известными дефектами диагностики](known-diagnostics-issues.md):
`discarded_bytes: 14 != 0` и ключ ошибки SFRBX с префиксом `02-13:`.
Их исправление вне scope. Дополнительные четыре теста формы добавлены после
загрузки тестов этого прогона; окончательные результаты приведены ниже.

Промежуточный расширенный прогон: 48 тестов, 47 PASS и 1 timeout в
`test_monitor_failure_retains_owner_until_actual_completion`. Изолированное исполнение
завершилось корректно за 10.131 s после увеличения тестового deadline с 8 до 15 s.
Добавлены значения состояния в сообщение о таймауте. Гипотеза о гонке запуска
не подтвердилась: `RecordingHandle.result(wait=True)` использует completion Event.
Экспериментальное изменение синхронизации удалено; алгоритм запуска не менялся.

Окончательный полный прогон с четырьмя новыми проверками формы:
**353 total: 350 PASS, 2 известных FAIL, 1 SKIP, 0 ERROR**, 64.732 s.
Команда: `python -m unittest discover -s tests -q`; exit 1 обусловлен только
двумя известными FAIL диагностики. Все тесты Stage 4.3 в этом прогоне прошли.
Пропуск — аппаратный regression с пользовательской записью, отсутствующей в fixture.
`git diff --check` — без ошибок; редакторская проверка шести GUI-модулей — без ошибок.
Независимый CLI `python -m gnss_logger --help` — exit 0.
Финальный связанный прогон Stage 4.2/4.3: **48/48 PASS**, 24.997 s.

## Постоянный запуск и временное окружение

Временная GUI-venv предыдущего этапа находилась в служебном temp-каталоге.
При продолжении работы она отсутствовала; конкретный процесс удаления не установлен.
Поэтому её нельзя использовать как постоянный пользовательский runtime.

Создана постоянная отдельная venv: `C:/Users/user/AppData/Local/GNSS/.venv-gui`.
Основная `.venv` не изменялась. Новая EXE-сборка не создавалась; старая сборка Stage 4.2
не содержит Stage 4.3. Исходники GUI хранятся в репозитории, а не в temp.

Запуск из любого текущего каталога, без установки проекта в editable mode:

```powershell
& 'C:/Users/user/AppData/Local/GNSS/.venv-gui/Scripts/python.exe' 'C:/Users/user/AppData/Local/GNSS/src/gnss-logger/tools/launch_gui_stage4_2.py' --mock
```

Имя launcher сохранено для совместимости; он импортирует текущий `app.main`.
Запуск этой команды с `--smoke-test` из родительского каталога GNSS дополнительно
проверен после финальных изменений: exit 0, passed=true, heartbeat=53,
ui_thread_delivery=true. Зависимости от текущего Git-каталога для launcher нет.
Без `--mock` включается production backend. Реальное устройство проверять только
по отдельному разрешению пользователя; этот отчёт такой проверки не утверждает.
Временные результаты smoke не предназначены для долговременного хранения.

## Ограничения и следующий этап

GUI-конвертация, история результатов и редактор настроек ещё не подключены:
это последующие этапы. Автоматическая конвертация из GUI на Stage 4.3 отключена.
Не выполнялись ручная проверка отрисовки/DPI/accessibility, физическое отключение USB
и аппаратная запись через GUI. Не создавались commit/push и новая EXE.
Не добавлены reconnect или принудительное завершение зависшего API: корректное закрытие
ждёт завершения существующего ядра; аварийное завершение потока не применяется.
Показатель phase_quality не доказывает отсутствие cycle slips.

Итог: программная реализация Stage 4.3 проверяется offline; аппаратная проверка
остаётся отдельным этапом. Stage 4.4 автоматически не начинается.
