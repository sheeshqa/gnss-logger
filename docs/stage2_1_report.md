## 1. Реализовано

- Типизированные Protocol для Controller, Reader, Journal, Rotator, Reconnector, Recovery
  и StopSignal; без runtime-реализаций этих компонентов.
- Состояния STARTING/IDENTIFYING/RECORDING/DISCONNECTED/WAITING/STORAGE_ERROR/STOPPING/STOPPED
  и проверка допустимых переходов. Повторный вход в RECORDING без идентификации запрещён.
- Неизменяемые InputChunk, RawRecord, RecordSettings, DeviceBinding, TimeBinding,
  ByteAccounting и WriteReceipt, проверки их базовых инвариантов.
- Строгие версионированные схемы manifest/event/diagnostic/checkpoint и чистый валидатор
  структуры/семантики; опубликованы JSON Schema, проверяемые на совпадение с Python-кодом.
- CLI-контракты record/status/verify/recover. Разбор и --help работают; исполнение возвращает
  4 / NOT_IMPLEMENTED без открытия порта, чтения входов, создания выходов и audit-каталогов.
- Правила UTC, идентификации, сегментации, учёта данных, checkpoints и будущей recovery
  зафиксированы в [stage2_1_contracts.md](stage2_1_contracts.md).

Запись многосуточных файлов, очередь исполнения, фоновые потоки, reconnect, восстановление,
публикация manifest, новый UTCWriter и реальный мониторинг ещё отсутствуют. Проверки
контрактов не выдаются за работающие гарантии многосуточной регистрации.

## 3. Архитектурные решения и причины

| Решение | Причина |
|---|---|
| Отдельный recording/ и новый record | Позволяет строить runtime без изменения поведения проверенного короткого CLI |
| Первичный byte journal + проекции daily/undated | Сохраняет повреждённые байты/хвосты и даёт воспроизводимое восстановление суточных файлов |
| run → attempt → connection → artifact | Исключает скрытое объединение после USB-разрыва/перезапуска и сохраняет происхождение |
| Три состояния времени, только RAWX для VALID | Не подменяет достоверный UTC часами ноутбука и не датирует измерения искусственно |
| VID/PID + model + явный serial либо location | COM может меняться; молчаливый выбор похожего устройства запрещён |
| Учёт received/written/synced/pending/unarchived | Различает получение, принятие файловой записью и подтверждение синхронизации |
| received_count_exact=false после неопределённого аварийного хвоста | Не маскирует неизвестную потерю как нулевую |
| Source ranges [start,end) с контролем порядка/пересечений | Проверяет побайтовое происхождение проекций, исключает дубль и перестановку |
| Независимые registration, phase_quality, integrity, hardware_validation | Успех записи не равен научной пригодности или аппаратной сертификации |
| Schema v1 отдельно от версии программы, strict fields + extensions | Даёт проверяемые форматы и возможность будущих независимых потребителей |
| Только keep_all, automatic_delete=false | Будущая политика хранения предусмотрена без разрешения удалять исходники |
| NOT_IMPLEMENTED/4 вместо фиктивного успеха | Пользователь не может принять заготовку record/verify за работающую регистрацию/проверку |

Исходные байты данных не передаются через изменяемые модели измерений. Проекция должна
копировать исходный FRAME, а не собирать пакет заново. На уровне контрактов проверяются
диапазоны и учёт; фактическая побайтовая сверка/CRC проекций относится к исполнителям 2.3/2.6.
Новых сторонних runtime-зависимостей нет; Protocol и валидатор используют стандартную библиотеку.

## 6. Спорные решения и вопросы согласования

1. **F9P без USB serial.** По Stage 1 serial отсутствовал. Binding через location+VID/PID+
   MON-VER имеет силу USB_TOPOLOGY: другой F9P в том же разъёме неотличим. Подтвердить,
   допустима ли такая ограниченная привязка для будущего автоматического reconnect,
   или требуется отдельное документированное read-only чтение уникального ID.
   Новый poll не добавлялся. До реализации 2.4 это ограничение нужно закрыть явно.
2. **Ресурсы 2.2/2.5.** Предлагаются queue 8 МиБ, sync 1 с, предупреждение 2 ГиБ и
   остановка при 512 МиБ с дополнительным учётом очереди/скорости. Это ещё не runtime-настройки;
   уточнить резерв на целевом ноутбуке и принять измеримый предел неподтверждённого хвоста.
3. **Время без привязки.** Предлагается сохранять initial/invalid/stale сообщения в undated
   без автоматического последующего «угадывания» суток. Точные пороги устаревания привязки,
   скачка RAWX и обработки изменения leapS согласовать с тестами подэтапа 2.3.
4. **Хранение двух представлений.** Primary и daily дублируют корректные кадры; расход
   планируется с этим учётом. Автоматическая очистка запрещена. Иные политики оставлены
   расширением контракта для будущего отдельного решения.

Эти вопросы не препятствуют приёмке архитектурного подэтапа; соответствующие runtime-политики
не выдаются за уже испытанные. До 2.2 нужны подтверждение этого отчёта и разрешение пользователя.

## 7. Итог и критерий перехода

Все критерии 2.1 выполнены: контракты/схемы/CLI определены, автономная регрессия проходит,
read-only и совместимость Stage 1 сохранены, исходные данные неизменны.

**Stage 2.1 готов к согласованию. Stage 2.2 не начат.** Следующий подэтап — исполнение
контроллера, единственного читателя, ограниченной очереди, исходного журнала и управляемой
остановки с самостоятельными fault tests и инструкцией аппаратного прогона 30–60 минут.
Суточная ротация, reconnect, recovery и мониторинг остаются последующими подэтапами.
