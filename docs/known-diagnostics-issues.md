## Исправления 2026-11-26 (offline Stage 4.6)

- **DIAG-01:** `UBXParser.feed_records()` вычислял `keep` для всего NMEA suffix,
  но оставлял только `buffer[-1:]`. Вдобавок `_incomplete_nmea_start()` отвергал
  последний CR, хотя следующий LF мог прийти отдельным блоком. Теперь сохраняется
  весь `[-keep:]`, разрешён завершающий CR без embedded CR/LF. Граница буфера
  остаётся прежней. Новые проверки подтверждают побайтовое равенство
  `emitted + buffer == consumed input`, правильный NMEA accounting и восстановление
  после 1000 байт незавершённой строки без неограниченного роста буфера.
- **DIAG-02:** контракт `Diagnostics.feed()` уже квалифицирует ошибки UBX
  идентификатором class/message. В тесте ожидалась строка без `02-13:`;
  теперь проверяется точный словарь с одним квалифицированным ключом и счётчиком 1.
  Формат диагностических отчётов и production mapping ошибок не изменялись.

Сначала подтверждены исходные 2 FAIL / 23 tests; после исправления 25/25 PASS
(1.188 с, существующая `.venv-gui`, Python 3.15.1). Аппаратура не использовалась.

### Cancellation/cleanup: ошибка выбора тестового процесса

Intermittent из [Stage 4.5a–b](stage4_5_ab_report.md) воспроизведён на отдельном
26-м запуске (серия 62.95 с). После добавления подробностей assertion — ещё раз
на 43-м запуске (79.36 с): отчёт содержал WinError 32 удаления пустого cwd.
Успешные серии до исправления (100/100 за 196.40 с и 100/100 за 192.10 с)
не считались доказательством устранения дефекта.

Проверка исполнения выявила Windows venv redirector: `sys.executable` запускал
ещё один Python. Наблюдались Popen PID 7684 / payload PID 9580; при использовании
`sys._base_executable` — один и тот же PID 12668. Отдельная проверка показала,
что после kill+wait redirector payload ещё жил (`WaitForSingleObject == 258`).
Следовательно, прежний тест мог отменять не тот процесс, который держал cwd.

Исправляется тестовый запуск, не production конвертер: stdlib payload запускается
непосредственно базовым интерпретатором. Перед Cancel проверяется, что PID,
записанный исполняемым payload, совпадает с Popen.pid. Проверки отсутствия
`.convbin-*`, сохранности первой публикации/исходных UBX и завершения child
не ослаблены; retry/задержек production cleanup не добавлено.

Та же предпосылка устранена в [test_gui_conversion.py](../tests/test_gui_conversion.py)
и [test_stage23_crash.py](../tests/test_stage23_crash.py): cancel/force-kill направлен
на действительный payload, готовность подтверждается содержимым PID barrier,
а не только появлением пустого файла. Связанные наборы — 11/11 и 1/1 PASS.

Это не реализация произвольной отмены дерева процессов. Управление native convbin
остаётся прежним; запуск фактического RTKLIB и аппаратные проверки не выполнялись.
Окончательный вариант: **20/20 PASS за 38.298 с и 100/100 PASS за 162.573 с**,
отдельные последовательные процессы. Общая регрессионная серия приведена ниже.

При внедрении PID-проверки промежуточный barrier с rename дал PermissionError
на 17-м запуске серии. Этот FAIL не подменялся успешным повтором: синхронизация
изменена на закрытие PID-файла перед публикацией отдельного ready-маркера.
Ожидание готовности остаётся ограниченным исходным deadline, PermissionError
не подавляется, production cleanup и его время не менялись.

### Критерий стабильной offline-регрессии

Три последовательных полных запуска на неизменном коде, без параллельной сборки
или stress-процессов, с остановкой при первом ненулевом exit code:

```powershell
$env:QT_QPA_PLATFORM = 'offscreen'
for ($run = 1; $run -le 3; $run++) {
    & C:\Users\user\AppData\Local\GNSS\.venv-gui\Scripts\python.exe -m unittest discover -s tests -q
    if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }
}
```

## Подтверждение независимости от доработки конвертера

До коммита конвертера выполнены два указанных ниже теста с подстановкой
`gnss_logger.conversion.cli` и `gnss_logger.conversion.engine` из Git-коммита
`f532f4e9a3f7a85a305be3efff4ea39247bee8de` (исходный HEAD до доработки).
Исходники загружены через `git show HEAD:<path>` и importlib в память процесса;
рабочие файлы не заменялись. Python 3.15.1, unittest: 2 теста, 2 FAIL,
те же assertion messages, что и с изменённым конвертером.

Таким образом, сбои воспроизводятся без доработки конвертера. Это известные
проблемы ранее изменённого рабочего состояния диагностики, а не утверждение
о наличии этих же сбоев в чистом Git-коммите: изменения декодера, диагностики
и её тестов уже присутствовали в рабочем дереве до начала задачи конвертера.
Они не входят в коммит конвертера и сохраняются без изменений.

## DIAG-01 — discarded_bytes в смешанном потоке

- Тест: `ProtocolTests.test_all_chunk_boundaries_and_mixed_stream`.
- Место: [test_diagnostics.py](../tests/test_diagnostics.py), строка 90.
- Ожидание: `d.parser.discarded_bytes == 0`.
- Фактически: `14`; assertion `14 != 0`.
- Следующее действие: отдельно исследовать содержимое этих 14 байт и правила
  классификации/буферизации на границах блоков. Не менять ожидание теста до
  установления причины.

## DIAG-02 — несовпадение ключа ошибки SFRBX

- Тест: `ProtocolTests.test_sfrbx_length_mismatch_is_not_counted`.
- Место: [test_diagnostics.py](../tests/test_diagnostics.py), строка 135.
- Ожидаемый ключ: `Invalid SFRBX word count or payload length`.
- Фактический ключ: `02-13: Invalid SFRBX word count or payload length`.
- Следующее действие: отдельно согласовать контракт ключей диагностических
  ошибок и затем исправить тест или реализацию согласно этому контракту.

Полный прогон после доработки конвертера: 216 тестов, 213 успешных,
2 вышеописанных FAIL, 1 SKIP. Связанные тесты конвертера: 34/34 успешны.
