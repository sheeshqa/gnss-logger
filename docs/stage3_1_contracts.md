# Stage 3.1 — конвертация завершённых UBX

`python -m gnss_logger convert` запускает отдельную операцию над закрытыми файлами.
Её можно выполнить на ноутбуке без подключённого GNSS-приёмника. RTKLIB требуется
только при вызове `convert`. Входные сегменты передаются в convbin по одному.

## Windows 10

Выполните команды из корня проекта в существующем виртуальном окружении.
Извлеките Windows-архив RTKLIB отдельно и найдите `convbin.exe`. Архив исходников
`RTKLIB-main` содержит C-код и требует сборки. Windows-бинарники доступны в
[разделе Releases проекта RTKLIB-EX](https://github.com/rtklibexplorer/RTKLIB/releases).
При смене сборки измените `engine.executable` и повторите dry-run. Для сравнения
результатов используйте разные выходные каталоги и сверяйте SHA-256 executable в отчётах.

```powershell
$Py = (Resolve-Path '.\.venv\Scripts\python.exe').Path
& $Py -m pip install -e .
& $Py -m pip check
$Base = Join-Path $env:LOCALAPPDATA 'GNSS'
$Cfg = Join-Path $Base 'conversion.local.toml'
New-Item -ItemType Directory -Path $Base -Force | Out-Null
if (!(Test-Path -LiteralPath $Cfg)) {
    Copy-Item -LiteralPath 'config\conversion.template.toml' -Destination $Cfg
}
notepad $Cfg
```

В TOML задайте фактический `engine.executable`. Например, литерал
`'C:\GNSS tools\RTKLIB\bin\convbin.exe'` поддерживает пробелы. Путь относительно
TOML разрешается от его каталога. Поддерживаются `%LOCALAPPDATA%` и другие переменные
окружения. По умолчанию команда ищет `%LOCALAPPDATA%\GNSS\conversion.local.toml`,
затем использует встроенные настройки. Для executable по умолчанию проверяются
PATH и путь `%LOCALAPPDATA%\GNSS\tools\convbin.exe`.

```powershell
& $Py -m gnss_logger convert --config $Cfg --dry-run
& $Py -m gnss_logger convert --config $Cfg
$RunId = Read-Host 'run_id из manifest'
& $Py -m gnss_logger convert --config $Cfg --run-id $RunId --dry-run
& $Py -m gnss_logger convert --config $Cfg --input 'D:\GNSS archive\UBX1_20261030_009.ubx'
& $Py -m gnss_logger convert --config $Cfg --input 'D:\GNSS archive\UBX1\2026\10' --output 'D:\GNSS exports\retest'
```

В последней команде задаётся новый каталог для повторной конвертации. По умолчанию
OBS, NAV и JSON размещаются в `%LOCALAPPDATA%\GNSS\data\rinex`. Базовое имя каждого
файла берётся из UBX. Выходные флаги `output.obs` и `output.nav` независимы.
Существующий OBS или NAV блокирует публикацию пары. Dry-run показывает argv,
планируемый временный рабочий каталог и конечные пути в stdout. Он выполняет
проверку интерфейса convbin и хеширует выбранные UBX.

## Выбор записей

- `--input` принимает завершённый `.ubx` или каталог. Каталог перечисляется на одном
  уровне в порядке имён. `.ubx.part`, пустые файлы и ссылки на файлы исключены из
  допустимых входов. Для внешнего архива оператор отвечает за завершённость записи.
- `--run-id` ограничивает поиск указанным UUID. Без явного входа выбирается успешный
  terminal manifest по `ended_utc`, с детерминированным разрешением совпавших времён.
  Отсутствие подходящего manifest требует явного `--input`.
- Для v2 выбираются все закрытые производные артефакты в порядке исходных смещений,
  включая `undated`. Проверяются их владельцы, число артефактов, границы настроенных
  каталогов и SHA-256 входа. Короткие сегменты с недостатком наблюдений получают
  собственный статус. Для v1 используется завершённый primary.
- Manifest привязан к путям, записанным на исходном компьютере. Для перенесённых
  архивов используйте явный файл или каталог.

## Профиль RTKLIB и RINEX

Версия зафиксирована на **3.02** для текущего `gnss_tec`. По умолчанию выбираются
GPS, GLONASS, Galileo, BeiDou и C/L/D/S. Code и phase входят в базовый вывод convbin.
Ключи `-od` и `-os` включают Doppler и SNR. Ключ `-y` повторяется для исключаемых
систем. Ключ `-f` задаёт верхний слот, а `-mask` выбирает конкретные коды сигналов.

| Группа | Маски профиля и слоты |
|---|---|
| L1 | GPS 1C, GLONASS 1C, Galileo 1B/1C/1X, BeiDou B1I 2I в RTKLIB. Слот 1 |
| L2/E5b | GPS 2L/2S/2X, GLONASS 2C, Galileo 7I/7Q/7X, BeiDou 7I. Слот 2 |
| L5/E5a | GPS и Galileo 5I/5Q/5X. Слот 3 |
| L6 | Galileo 6A/6B/6C/6X, BeiDou B3I 6I. Слот 4 |

Например, E5b I задаётся как `EL7I`, B1I как `CL2I`. В исходниках EX 2.5.1
запись B1I в заголовке 3.02 использует `1I`. Проверка сопоставляет это с внутренним
кодом `2I`. Явный `signal_masks` задаёт точный список, включая X-коды при
необходимости. EX может объединять коды при декодировании. Слот ограничивает
вывод и сам по себе не добавляет частоты или возможности конкретной сборки.

GPS/GLONASS L6 и GLONASS L5 в этом профиле отсутствуют. Современные BeiDou B1C/B2a
отсутствуют в поддерживаемом наборе 3.02. Неподдерживаемые маски в TOML дают ошибку.
Для имеющихся RAWX в выбранных системах неизвестные сигналы и пропавшие выбранные
коды дают предупреждение. Отдельно перечисляются запрошенные группы без пригодных
данных. Таким образом, запрос L5 или L6 не подразумевает, что F9P их записал.
Профиль основан на локальных `ublox.c`, `rtkcmn.c`, `convrnx.c` и `rinex.c`
и спецификации [IGS RINEX 3.02](https://files.igs.org/pub/data/format/rinex302.pdf).

## Проверки и отчёт

При запуске без аргументов или через `--help` проверяются опции сборки и UBX.
`--version` пробуется как необязательный интерфейс. Отчёт хранит help, доступную
версию, хеш и путь executable. Перед вызовом convbin создаётся временная копия
UBX с простым относительным именем. Команда запускается списком аргументов
через `shell=False`. Хеши источника и executable повторно сверяются перед публикацией.

OBS проверяется по версии, типу, заголовку, эпохам и числовым наблюдениям.
NAV проверяется по версии, типу, заголовку и полным числовым блокам сообщений.
Для RINEX 3.02 исходники EX 2.5.1 направляют данные нескольких систем в `-n`
при отключённом режиме раздельной навигации. Дополнительные файлы NAV не
объединяются переименованием. Если есть раздельный вывод, отсутствует пригодный
NAV или в нём отсутствует выбранная система с SFRBX, статус **INCOMPLETE_NAVIGATION**.
Наличие SFRBX показывает наличие фрагментов навигационных сообщений. Полный набор
эфемерид по этому счётчику установить нельзя. При неполной паре конечные OBS/NAV
этого сегмента не публикуются.

`conversion-<operation_id>.json` содержит параметры, команду и cwd, информацию
о входе, stdout/stderr subprocess, код завершения, хеши опубликованных файлов,
результаты проверки и ошибки. Для логов сохраняется до 64 КиБ на поток.
Успешные статусы `SUCCESS` и `SUCCESS_WITH_WARNINGS` возвращают 0.
`INCOMPLETE_NAVIGATION` возвращает 3, `FAILED` возвращает 1,
`INTERRUPTED` возвращает 130. `DRY_RUN` возвращает 0.
Отчёт публикуется последним. Пара файлов в плоском каталоге не составляет одной
атомарной операции при принудительном завершении процесса или потере питания.
При обычной ошибке публикации собственный уже опубликованный файл пары удаляется.
Для принятия результата проверьте JSON, `published_outputs` и SHA-256.

Конвертация сохраняет границы входных сегментов. Отчёт учитывает интервалы OBS
с отклонением более 10% от `input.interval_s` и границы между соседними результатами
с одинаковой указанной шкалой времени. Он хранит расхождения числа эпох с RAWX.
Решение об абсолютной точности TEC и непрерывности фазы требует отдельной проверки.
